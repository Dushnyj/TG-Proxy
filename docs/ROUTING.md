# Маршрутизация

## Задача

Маршрутизация должна подбирать стабильный способ доставки MTProto-трафика Telegram для текущей сети. Один и тот же маршрут может хорошо работать в домашнем Wi-Fi и полностью не работать у мобильного оператора.

## Кандидаты маршрутов

### Direct WS

Прямой WebSocket к Telegram Web endpoint через IP, указанный в DC mapping.

Пример:

```text
DC2 -> 149.154.167.220
DC4 -> 149.154.167.220
```

Этот маршрут быстрый, если сеть его пропускает. Если оператор режет `149.154.167.220:443`, Direct WS должен быстро получить статус `degraded` и не блокировать работу приложения.

### VPS Relay

Личный relay-сервер пользователя. Приложение подключается к VPS, а VPS подключается к Telegram DC.

Это основной стабильный fallback, когда Direct WS не проходит, а публичный Cloudflare нестабилен.

### Cloudflare Worker

Пользовательский Worker endpoint. Он может быть стабильнее публичного пула, но зависит от настроек Cloudflare и лимитов аккаунта.

### Пользовательские Cloudflare-домены

Домены пользователя, заведенные через Cloudflare. Они должны иметь приоритет выше публичного пула, потому что пользователь контролирует домен и лимиты.

### Публичный Cloudflare-пул

Публичные домены, совместимые с Flowseal-подходом. Это последний внешний fallback. Его нельзя считать надежным основным маршрутом: домены могут получать HTTP `429`, временно отваливаться или быть недоступными у конкретного оператора.

### TCP fallback

Прямой TCP fallback используется только как крайний резерв. Если сеть режет Telegram IP, этот маршрут будет уходить в timeout.

## Автовыбор

Приложение должно выбирать маршрут по стабильности, а не по одному пингу.

У каждого маршрута есть оценка:

```text
score = latency + p95 penalty + error penalty + cooldown penalty + switch penalty
```

В оценку входят:

- успешность handshake;
- median и p95 задержки;
- timeout rate;
- reset rate;
- HTTP 429 rate;
- наличие реального трафика;
- время последнего успешного подключения;
- частота переключений.

## Правила переключения

1. Если текущий маршрут работает, не менять его из-за одного лучшего пинга.
2. Новый маршрут должен пройти несколько проверок подряд.
3. Старые рабочие соединения не закрывать без причины.
4. Новые подключения можно переводить на новый маршрут после прогрева.
5. Если текущий маршрут умер, переключаться сразу на лучший доступный fallback.
6. Маршрут с `429` или timeout уходит в cooldown.
7. После cooldown маршрут можно проверить снова.

## Приоритеты по умолчанию

Для Wi-Fi:

```text
Direct WS -> VPS Relay -> Worker -> custom Cloudflare -> public Cloudflare -> TCP fallback
```

Для мобильной сети:

```text
VPS Relay -> Worker -> custom Cloudflare -> public Cloudflare -> Direct WS -> TCP fallback
```

Это только стартовый порядок. После сбора статистики профиль сети может выбрать другой маршрут.

## Пинг

Пинг на главном экране проверяет только активный маршрут. Он не должен каждый раз перебирать Cloudflare-домены или менять активный домен.

Полная проверка всех маршрутов находится в диагностике и запускается вручную или фоново с ограничением частоты.

## Telegram DC mapping

Пользователь может оставить DC mapping пустым, указать один DC или несколько DC.

Поддерживаемые варианты:

```text

```

```text
4:149.154.167.220
```

```text
2:149.154.167.220
4:149.154.167.220
```

Правила:

- пустой список означает автоматические безопасные значения;
- одна строка покрывает только один DC;
- недостающие DC должны уходить через VPS/Worker/Cloudflare fallback;
- неправильный формат не сохраняется;
- если новый конфиг невалиден, приложение оставляет предыдущий рабочий конфиг;
- диагностика показывает результат по каждому DC main/media.

В интерфейсе основной режим должен быть табличным:

```text
DC 2    149.154.167.220
DC 4    149.154.167.220
```

Расширенный текстовый ввод нужен только для опытных пользователей.
