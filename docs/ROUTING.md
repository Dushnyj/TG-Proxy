# Маршрутизация

## Задача

Маршрутизация должна подбирать стабильный способ доставки MTProto-трафика Telegram для текущей сети. Один и тот же маршрут может хорошо работать в домашнем Wi-Fi и полностью не работать у мобильного оператора.

## Кандидаты маршрутов

### Direct WS

Прямой WebSocket/TLS к официальному Telegram Web endpoint. Для подтверждённых DC1-5 приложение
гоняет встроенный bootstrap IP и актуальное DNS-разрешение `kws<dc>.web.telegram.org`, сохраняя
фактический победивший endpoint для диагностики и независимого MTProto probe.

Новый DC сам по себе не превращается в `kws204`: официальный WebSocket ingress должен быть
подтверждён отдельно. Поэтому unknown DC для Direct честно `unsupported`, а не ложный candidate.
Если оператор режет Telegram IP/hostname, Direct быстро получает `degraded` и не блокирует
работу остальных маршрутов.

### VPS Relay

Личный relay-сервер пользователя. Приложение подключается к VPS, а VPS подключается к Telegram DC.

Это основной стабильный fallback, когда Direct WS не проходит, а публичный Cloudflare нестабилен.
Relay 1.3.0 может получить подписанную topology, хранить несколько endpoints на DC и пережить
смену IP/port или новый DC без обновления APK. Если dynamic topology не настроена, применяется
статическая карта и unknown DC не рекламируется Android.

### Cloudflare Worker

Пользовательский Worker endpoint. Он может быть стабильнее публичного пула, но зависит от настроек Cloudflare и лимитов аккаунта.

### Пользовательские Cloudflare-домены

Домены пользователя, заведенные через Cloudflare. Они должны иметь приоритет выше публичного пула, потому что пользователь контролирует домен и лимиты.

### Публичный Cloudflare-пул

Публичные домены, совместимые с Flowseal-подходом. Это последний внешний fallback. Его нельзя считать надежным основным маршрутом: домены могут получать HTTP `429`, временно отваливаться или быть недоступными у конкретного оператора.

## Выключатели маршрутов

Вкладка `Настройки -> Маршруты` хранит отдельную маску для каждого сетевого профиля:

- Direct;
- VPS Relay;
- Cloudflare Worker;
- свой Cloudflare;
- публичный Cloudflare.

`Только Direct` выключает остальные четыре типа одной командой. Нельзя сохранить профиль, где
выключено всё. После выключения route новые подключения больше не получают его candidate, а
уже открытые сессии этого route закрываются без остановки остальных соединений.

## Автовыбор

Приложение выбирает маршрут по стартовому порядку текущего профиля и накопленной статистике,
а не по одному измерению задержки.

У каждого маршрута есть оценка:

```text
score = 10000 - orderIndex * 100
      + min(successCount, 4) * 20
      + max(-80, 80 - medianLatencyMs / 5)
      - totalFailures * 35
      - errorTypePenalty
```

`errorTypePenalty` дополнительно равен `60` при наличии HTTP 429, `50` для timeout и `45`
для reset. История маршрута хранится 12 часов; неактуальная статистика очищается.

Успех записывается не после одного HTTP `101`, а после первого валидного ответа Telegram.
Последующий upload и download трафик освежает время живого маршрута. Main/media и разные DC
имеют разные ключи статистики, поэтому сбой голосового сообщения не охлаждает main-route.

## Правила переключения

1. Если текущий маршрут работает, не менять его из-за одного лучшего пинга.
2. Для переключения на «лучший» маршрут нужны минимум три успеха и преимущество не менее 120
   баллов; это защищает от дребезга.
3. Старые рабочие соединения не закрывать без причины.
4. Новые подключения можно переводить на новый маршрут после прогрева.
5. Если текущий маршрут умер, переключаться сразу на лучший доступный fallback.
6. Маршрут с `429`, timeout, reset, DNS/TLS или protocol failure уходит в cooldown на 10–45
   секунд в зависимости от ошибки.
7. После cooldown маршрут можно проверить снова.
8. Если охлаждены все маршруты, ровно один earliest half-open probe получает lease; burst
   переподключений Telegram не должен одновременно атаковать один endpoint.

## Приоритеты по умолчанию

Для Wi-Fi:

```text
Direct WS -> VPS Relay -> Worker -> custom Cloudflare -> public Cloudflare
```

Для мобильной сети:

```text
VPS Relay -> Worker -> custom Cloudflare -> public Cloudflare -> Direct WS
```

Это только стартовый порядок. После сбора статистики профиль сети может выбрать другой маршрут.

Ручные режимы задают следующий стартовый порядок:

```text
Direct первым:     Direct -> VPS Relay -> Worker -> custom Cloudflare -> public Cloudflare
Cloudflare первым: custom Cloudflare -> Worker -> public Cloudflare -> VPS Relay -> Direct
Relay первым:      VPS Relay -> Worker -> custom Cloudflare -> public Cloudflare -> Direct
```

Ненастроенный тип просто пропускается. Пользовательские домены и Worker намеренно стоят перед
публичным Cloudflare-пулом: владелец контролирует их конфигурацию и лимиты.

## Пинг

Поле `Отклик MTProto` — не ICMP ping и не TCP-connect. Раз в 30 секунд оно проходит тот же
активный route и измеряет полный TCP/TLS/WebSocket/Relay handshake до валидного Telegram
`req_pq/resPQ`. Результат привязан к
`route key + фактический endpoint + фактический TLS SNI + service generation`.
Поздний callback старого endpoint/SNI отбрасывается. Ошибка вспомогательного probe не заменяет
свежую first-byte latency рабочего трафика значением `error`.

Полная проверка всех маршрутов находится в диагностике и запускается вручную или фоново с ограничением частоты.

## Расширенный Direct mapping

Пользователь может оставить mapping пустым, указать один DC или несколько DC. Это ручной
bootstrap/override Direct; он не заменяет Telegram `dc_options` и не делает Direct или Worker
автоматически динамическими. Worker использует собственный ограниченный allow-list raw targets.

Поддерживаемые варианты:

```text
(пусто: встроенный безопасный bootstrap)
```

```text
4:149.154.167.220
```

```text
2:149.154.167.220
4:149.154.167.220
```

Правила:

- пустой список означает автоматические безопасные значения;
- одна строка покрывает только один DC;
- route без знания недостающего DC не создаёт candidate; Route Engine пробует только реально
  поддерживающие этот DC fallback-маршруты;
- неправильный формат не сохраняется;
- если новый конфиг невалиден, приложение оставляет предыдущий рабочий конфиг;
- диагностика показывает результат по каждому DC main/media.

В интерфейсе основной режим должен быть табличным:

```text
DC 2    149.154.167.220
DC 4    149.154.167.220
```

Расширенный текстовый ввод нужен только для опытных пользователей.

Полная граница ответственности, включая media/CDN и synthetic DC204/-DC204, описана в
[TELEGRAM_TOPOLOGY.md](TELEGRAM_TOPOLOGY.md).
